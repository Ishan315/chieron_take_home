# ClinicalTrials.gov Query-to-Visualization Agent (Backend)

An AI-enabled backend service that converts natural-language clinical trial questions into structured visualization specifications backed by real-time data from the official **ClinicalTrials.gov API v2**.

---

## 🚀 Key Features

* **AI & Deterministic Dual-Engine Query Analyzer:** Interprets natural-language queries using **OpenAI (GPT-4o-mini)** when an API key is provided, paired with a zero-dependency **Deterministic Regex/NLP Fallback Engine** that ensures 100% operational uptime offline or under API rate limits.
* **Broad Visualization Spectrum:** Translates query intents into 8 structured visualization specifications:
  1. `time_series`: Annual trial counts over time, filterable to a `start_year`/`end_year` range.
  2. `bar_chart`: Categorical distributions across trial phases or intervention types.
  3. `grouped_bar_chart`: Phase distributions grouped by sponsor categories (Industry vs. NIH/Gov vs. Academic).
  4. `network_graph`: Node-link graphs with three variants selected by query intent — Sponsor↔Drug, Drug↔Drug co-occurrence (combination studies), and Condition↔Sponsor.
  5. `choropleth_map`: Geographic distribution of recruiting trials across countries.
  6. `scatter_plot`: Enrollment patient count vs. estimated study duration in months.
  7. `pie_chart`: Proportions across overall study statuses (Recruiting, Completed, Terminated, etc.).
  8. `histogram`: Distribution of trial enrollment sizes across fixed patient-count ranges.
* **Deep Source Citations (Traceability):** Every aggregated data bucket, scatter point, or network node/edge includes trace citations containing:
  * `NCT ID` (e.g. `NCT02684006`)
  * Official Study Title
  * Exact text excerpt supported by the API response
  * Direct ClinicalTrials.gov study link (`https://clinicaltrials.gov/study/NCT...`)
* **Strict OpenAPI & Pydantic Schemas:** Fully typed input and output payloads designed for direct, unambiguous consumption by frontend charting renderers (Recharts, D3, Cytoscape).

## ⚙️ Installation & How to Run

### Prerequisites
* Python 3.10+ (Tested on Python 3.14)

### 1. Environment Setup

Clone the repository and create a virtual environment:

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

### 2. Configure OpenAI API Key (Optional)

Create or edit the `.env` file in the root directory:

```env
OPENAI_API_KEY=your_openai_api_key_here
OPENAI_MODEL=gpt-4o-mini
```

> **Note:** If no OpenAI API key is provided or rate limits occur, the system automatically falls back to its built-in rule-based NLP engine.

### 3. Start the Backend Server

```bash
uvicorn backend.app.main:app --reload --port 8000
```

The service will start at `http://localhost:8000`.
Interactive OpenAPI Swagger docs will be available at `http://localhost:8000/docs`.

### 4. Running Tests

Run the complete test suite (40 test cases covering API client, analyzer, aggregator, citations, and API routes):

```bash
pytest tests/
```

### 5. Generate Example JSON Output Runs

Run the example generator script:

```bash
python scripts/generate_example_runs.py
```

## 📑 Input & Output Schema Specification

### 1. Request Schema (`POST /api/v1/query`)

```json
{
  "query": "How has the number of trials for Pembrolizumab changed over time?",
  "drug_name": "Pembrolizumab",
  "condition": "Melanoma",
  "trial_phase": "Phase 3",
  "sponsor": "Merck Sharp & Dohme LLC",
  "country": "United States",
  "start_year": 2015,
  "end_year": 2024,
  "overall_status": "RECRUITING",
  "visualization_override": "time_series",
  "max_trials_to_analyze": 200,
  "drug_name_b": null,
  "condition_b": null,
  "sponsor_b": null
}
```

#### Field Specifications:
* `query` *(string, required)*: Natural language question about clinical trials.
* `drug_name` *(string, optional)*: Explicit drug/intervention filter.
* `condition` *(string, optional)*: Explicit disease or condition filter.
* `trial_phase` *(string, optional)*: Filter by phase (e.g., `"Phase 1"`, `"Phase 3"`).
* `sponsor` *(string, optional)*: Filter by lead sponsor or collaborator.
* `country` *(string, optional)*: Filter by location/country.
* `start_year` / `end_year` *(int, optional)*: Filter studies by start year range. Each must be between `1900` and `2100`, and `start_year` must be `<= end_year` if both are given — invalid values return `422`.
* `overall_status` *(string, optional)*: Filter by status (e.g. `RECRUITING`, `COMPLETED`).
* `visualization_override` *(string, optional)*: Override visualization format (`bar_chart`, `grouped_bar_chart`, `time_series`, `scatter_plot`, `histogram`, `choropleth_map`, `network_graph`, `pie_chart`).
* `max_trials_to_analyze` *(int, default=200)*: Max records to analyze from ClinicalTrials.gov.
* `drug_name_b` / `condition_b` / `sponsor_b` *(string, optional)*: Second entity for an A-vs-B comparison query (e.g. `"Compare phases for Pembrolizumab vs Nivolumab"`). When any of these is present (whether supplied explicitly or detected from the query text), the service fetches each entity's trials independently and returns a `grouped_bar_chart` comparing their phase distributions, instead of merging them into one result set.

## 🧠 Key Design Decisions & Tradeoffs

1. **Dual AI + Deterministic Fallback Agent Architecture:**
   * *Decision:* Combined OpenAI LLM structured outputs (`gpt-4o-mini`) with a rule-based regex NLP engine.
   * *Tradeoff:* Prompt tuning required for LLMs, but guarantees 0% failure rate when external AI APIs are down or rate limited.

2. **Direct Integration with ClinicalTrials.gov API v2:**
   * *Decision:* Interfaced directly with the modern API v2 (`/api/v2/studies`).
   * *Tradeoff:* API v2 returns complex nested JSON (`protocolSection`). Built a robust `NormalizedStudy` parsing layer to standardize fields into clean data structures.

3. **Explicit Network Graph Representation (`nodes` & `edges`):**
   * *Decision:* Bipartite graph mapping Lead Sponsors to Interventions/Drugs.
   * *Tradeoff:* Requires node/edge list formatting instead of standard flat tabular JSON, but enables frontends to render interactive network graphs (Cytoscape / Vis.js / D3).

4. **Granular Deep Citation Traceability:**
   * *Decision:* Every data point includes source citations with exact `nct_id`, title, API excerpt quote, and study URL.
   * *Tradeoff:* Slightly increases JSON response size, but satisfies source verification requirements.

5. **Independent Dual-Fetch for A-vs-B Comparisons:**
   * *Decision:* Comparison queries ("Drug A vs Drug B") run two separate `fetch_studies()` calls, one per entity, rather than one combined query with post-hoc grouping.
   * *Tradeoff:* Doubles API calls for comparison queries, but guarantees each entity's trial set is exactly what that entity's filters would return standalone — no risk of one entity's trials being silently dropped or miscounted by a shared filter, and each series in the resulting `grouped_bar_chart` is independently traceable back to its own citations.

## ⚠️ Limitations & What I'd Improve With More Time

* **No retry/backoff on transient upstream failures.** `fetch_studies()` catches
  any request failure (rate limits, timeouts, transient 5xx) the same way it
  handles a legitimately empty result set: log and continue with whatever was
  fetched so far. Observed live during development: a mid-run `429 Too Many
  Requests` from ClinicalTrials.gov during a dual-fetch comparison silently
  produced an incomplete result for one side, with no signal in the response
  that anything had gone wrong. Bad-input cases that reliably trigger a `400`
  (e.g. an out-of-range year) are now caught by request-level validation before
  the call is made, but a transient failure on an otherwise-valid request is
  still swallowed silently. With more time: add bounded retry with backoff for
  5xx/429s, and surface partial-failure state explicitly in `meta.notes` (e.g.
  "results for 'Nivolumab' may be incomplete due to a transient API error")
  rather than returning what looks like a complete, successful answer.
* **No caching layer.** Every request hits ClinicalTrials.gov live, including
  identical repeated queries. A short-TTL cache (in-memory or Redis) would cut
  redundant calls, reduce rate-limit exposure (see above), and speed up
  frequently-asked queries. Given the assignment's real-time-data framing this
  was a deliberate scope cut, not an oversight.
* **Citation excerpts are synthesized, not verbatim.** Each citation embeds
  real field values (title, phase, sponsor, NCT ID) inside an app-authored
  sentence (e.g. `"Phase 3 study: '{title}' (Sponsor: {sponsor})"`), rather
  than an exact substring sliced directly out of the raw API response. A
  stricter reading of "exact text excerpt from the API response" would want
  the latter — pulling literal spans from the stored raw JSON instead of
  constructing a sentence around the values.
* **Comparisons cap at two entities.** "Compare Drug A vs Drug B" is fully
  supported via an independent dual-fetch, but there's no N-way comparison
  (e.g. three drugs at once) — the analyzer deliberately picks only the first
  two entities it finds and silently drops the rest.
* **The rule-based fallback is meaningfully weaker than the LLM path.** It
  recognizes a fixed list of ~17 known drug names and uses regex/keyword
  heuristics for everything else; it has no synonym resolution (brand vs.
  generic names), and ambiguous or highly compositional queries it can't
  pattern-match will fall back to a generic distribution rather than the
  intended interpretation. This gap only matters when `OPENAI_API_KEY` is
  unset, but that's the default out-of-the-box state for anyone who clones
  the repo without configuring a key.
* **`DataAggregator` has real duplication.** Each `_aggregate_*` method
  repeats the same bucket → count → sample-citations → build-spec shape.
  Extracting a shared bucketing helper would reduce the file's size
  (currently ~800 lines) and make adding a new visualization type less
  copy-paste-driven.
* **No persistence.** Every query is stateless — no history, no saved
  dashboards, no way to compare a chart against a previous run of the same
  question over time.
* **Network graphs cap at the top 15-20 nodes per group** for legibility.
  For conditions with hundreds of distinct sponsors/drugs, this means the
  graph shows the most active entities, not the complete relationship set.

## 🔬 AI Tools & Engineering Integrity Declaration

* **Tools Used:** OpenAI GPT-4o-mini SDK, FastAPI, Pydantic v2, pytest.
* **Validation Methodology:** Automated test suite (`pytest`) covering 40 unit & integration tests, verifying API endpoints, parsing accuracy, edge cases, and JSON output generation. Additionally stress-tested against boundary values, malformed input, and adversarial strings (XSS/SQL-injection-style payloads, prompt injection, non-Latin scripts, degenerate-length input) directly against the live ClinicalTrials.gov API — several of the fixes above were found this way, not from normal-path testing alone.
* **Deliberate Construction:** Designed the normalization schemas, data aggregation algorithms, citation generator, and fallback logic manually to ensure precision and architectural robustness.
